# 상품 대량 등록

플레이오토 엑셀 일괄등록으로 세 마켓에 상품을 올린다.
사용자는 개발자가 아니다. **검증·조사·판단은 전부 이쪽에서 한다.** 사용자에게 확인을 떠넘기지 않는다.

## 절대 규칙

- **소비자상담번호는 항상 판매자 번호 `010-6564-4459`.** 제조사 번호를 쓰지 않는다.
- **`registration_status = 판매중지`인 상품은 절대 건드리지 않는다.** 엑셀에도 넣지 않는다.
- **원 판매자의 상세페이지 이미지를 복사하지 않는다.** 저작권·개인정보 침해로 내려간 이력이 있다. 사실 정보(용량·원재료 등)만 가져온다.
- 상품명은 **한글·영문·숫자·공백만**. 특수문자 금지(소수점은 예외).
- LLM이 필요하면 Gemini API를 쓴다.
- 커밋·배포는 사용자 승인 후에만 한다.

## 전체 순서

```
1. 사전 점검      금칙어 · 용량 · 바코드
2. 엑셀 생성      build-playauto-excel.mjs
3. QA             qa-smartstore.mjs / qa-esm.mjs      ← 반드시 통과시킨 뒤 넘긴다
4. 사용자가 업로드  플레이오토 → 마켓 전송
5. 결과 분석      반려 원인 분류 → 고치고 재시도
6. 등록 후 정리    캐시 초기화 → 임포트 → 상태 갱신
```

## 1. 사전 점검

```bash
node scripts/scan-forbidden.mjs                    # 금칙어 검사
node scripts/fix-forbidden.mjs --apply             # 치환 규칙 적용
node scripts/fill-unit-size-koreannet.mjs --apply  # 이름에 용량 없는 상품 채우기
```

금칙어는 `forbidden_words` 테이블에 있다. 새로 발견하면 `forbidden-words-seed.mjs`에 넣고
`--apply`로 저장한다. **상품명·상세설명뿐 아니라 고시 24칸도 검사 대상이다** — 고시 칸이 상세페이지에 그대로 노출된다.

## 2. 엑셀 생성

```bash
node scripts/build-playauto-excel.mjs smartstore --chunk 300
node scripts/build-playauto-excel.mjs gmarket_auction --chunk 300
node scripts/build-playauto-excel.mjs coupang --chunk 300
```

파일은 `바탕화면/상품등록/`에 `플레이오토_<마켓>_<날짜>_1of4.xlsx` 꼴로 나온다.

**재시도할 때는 반드시 `--retry`를 붙인다.**

```bash
node scripts/build-playauto-excel.mjs smartstore --retry "<결과.xlsx>"
```

## 3. QA — 건너뛰지 않는다

```bash
node scripts/qa-smartstore.mjs        # 스마트스토어
node scripts/qa-esm.mjs               # 지마켓·옥션
```

"■ 등록을 막는 문제: 없음"이 나와야 사용자에게 넘긴다.
**새 반려 사유를 발견하면 그때마다 QA에 검사를 추가한다.** 같은 실수가 두 번 나오면 안 된다.

## 4. 결과 분석

사용자가 결과 엑셀을 주면 사유별로 묶어 원인을 밝힌다.

```bash
node scripts/analyze-result.mjs "<결과.xlsx>"
```

결과 파일은 두 종류다. 섞이지 않게 구분한다.

| 파일 | 판별 | 뜻 |
|---|---|---|
| 플레이오토 엑셀일괄등록 결과 | `결과` 컬럼 | 플레이오토에 상품이 만들어졌나 |
| 쇼핑몰 작업결과 | `작업결과` 컬럼 | 실제 마켓에 전송됐나 |

플레이오토에 만들어져도 마켓 전송은 실패할 수 있다. 그 경우 플레이오토에서 지우고 다시 올려야 한다
(`pa-delete-list.mjs`로 삭제 목록을 뽑는다).

## 5. 등록 후 정리

```bash
node scripts/clear-price-inventory.mjs <esm|smartstore|coupang> --apply   # 옛 캐시 비우기(백업됨)
```

그다음 사용자가 각 셀러센터에서 파일을 받아 임포트한다.

| 마켓 | 받는 곳 | 주의 |
|---|---|---|
| 스마트스토어 | 센터 → 상품관리 → 상품 일괄수정 | 받은 파일 그대로 |
| 지마켓·옥션 | ESM Plus → 상품관리 → 상품목록 | **가격대량수정 양식 아님** |
| 쿠팡 | WING → 상품 조회/수정 → 가격/재고 일괄변경 | P~S열이 빈 파일이 맞다 |

임포트는 캐시만 채우는 게 아니라 **`platform_codes`에 마켓 상품번호를 넣는다.** 이게 없으면 가격수정이 안 나간다.
상품을 새로 등록한 뒤에는 **반드시 캐시를 비우고 다시 임포트한다.** 임포트는 상품번호 기준 upsert라
옛 행이 그대로 남는다.

## 6. "양식 행이 없어 제외됨" — 재임포트로 해결되지 않는다

자동 가격갱신 로그(`scripts/logs/auto-price-*.log`)에 뜨는 이 문구를 **양식이 낡은 탓으로 진단하지 않는다.**
2026-08-25에 새 양식을 받아 임포트해도 연결 수는 그대로였다(921개). 원인은 둘 중 하나뿐이다.

| 원인 | 판별 | 조치 |
|---|---|---|
| 마켓에 **등록 자체가 안 된** 상품 | 셀러센터 상품 수 < DB 상품 수 | 실제 등록 필요. **재임포트 무의미** |
| `판매중지` 상품 | `registration_status` | 정상. 조치 없음 |

2026-08-25 실측 — 쿠팡 249개(판매중 226) / 스마트스토어 107개(73) / ESM 34개(3, 나머지는 판매중지).
쿠팡 셀러센터 922종 vs DB 1,170개 → 약 250개가 쿠팡 미등록.

**매칭은 쿠팡 `H열 = 업체 등록 상품명`과 `products.product_name`의 완전일치다**
(`normalizeName`은 trim + NFC만 한다). 글자 하나만 달라도 안 붙는다.
실제 사례: DB `…제로칼로리 콜라` vs 쿠팡 `…제로칼로리 다이어트 콜라`.

임포트 모달의 **"미매칭 상품"은 *쿠팡에 있는데 DB에 없는* 것**이다. 방향이 반대이므로,
DB에만 있는 상품은 모달에 뜨지 않는다 — `*_price_inventory`의 `product_id` 집합과
`products`를 직접 비교해야 보인다.

> 상품명 유사도로 "이름만 다른 것"을 자동 분류하려 시도했으나 오탐이 심했다
> (헛개차↔게토레이가 80%로 잡힘). 향·맛 변형이 많은 상품군에서는 신뢰할 수 없다.

# 겪은 함정 (전부 실제로 반려·사고가 났던 것)

## 판매자관리코드를 통째로 새로 발급하는 사고 — 가장 위험

`--retry` 없이 다시 생성하면 **전 상품에 새 코드가 발급되고 DB를 덮어쓴다.**
이미 마켓에 올라간 상품이 중복 등록되고, DB와 마켓이 어긋난다.

```bash
# 결과 엑셀의 실제 등록 코드로 되돌린다
node scripts/restore-seller-code.mjs smartstore "<결과.xlsx>" --apply
```

`restore-seller-code.mjs`는 **상품명으로 찾는다.** 이름이 같은 상품이 둘이면 한쪽만 고쳐지므로,
이름 중복이 있는지 먼저 확인한다.

마켓에서 그 묶음을 통째로 지운 상태라면, 코드를 지킬 이유가 없으니 **전체 재생성이 더 깔끔하다.**

## 쿠팡

- **GTIN은 상품 1개당 유일.** 묶음수량 변형(210ml 30개/60개)은 낱개 바코드가 같아 두 번째부터 반려된다.
  → 상품참조번호를 올리고 체크디짓을 다시 계산한 변형 GTIN을 쓴다(`--altbarcode`).
  이미 성공한 번호는 `claimed-barcodes.mjs`가 모아둔 목록에서 피한다.
- **`옵션바코드` 컬럼이 GTIN으로 전송된다.** 마스터 `바코드`/`표준상품코드`만으로는 반려.
- **`모델번호`/`옵션 모델번호`가 MPN으로 전송된다.** 바코드가 없을 때 품목보고번호를 넣는다.
  단, GTIN만 받는 카테고리가 많아 성공률은 낮다.
- **필수옵션은 전부 채우거나 아예 만들지 않는다.** 반쪽은 "필수 추천 옵션을 모두 선택해주세요"로 반려.
- **단위 표기가 항목마다 다르다.**
  ```
  개당 수량 → 개입·롤·매·세트   ("개"는 거부)
  수량/총수량 → 개·박스·세트     ("개입"은 거부)
  총 수량 → 개입                 (에너지/비타민음료·녹차티백·커피믹스만)
  ```
- **모델명에 특수문자(•, ·, -)가 있으면 반려.**
- 플레이오토가 우리 카테고리를 자기 기준으로 다시 매핑한다.
  `lib/coupang-category-options.ts`는 참고일 뿐, **업로드 결과가 유일한 근거다.**

## 스마트스토어

- **표시 용량은 1~999만 받는다.** 단위가격을 안 쓸 때 `0`을 넣으면 반려된다 → **빈칸**으로 둔다.
  (실제로 이것 때문에 124건이 한 번에 반려됐다)
- 표시 여부가 Y면 구성 방식·팩 수량·팩당 수량·개당 용량이 전부 있어야 한다.
- **고시의 "유전자변형식품", "수입신고 필함 문구"는 Y/N만.** "해당없음"은 반려.
- **카테고리코드는 `smartstore_category_codes`에 실제로 있는 코드만.** 상위·유사 카테고리로 보내면
  쿠팡 필수옵션까지 달라져 연쇄로 반려된다.
- 품목고시 코드: 17 주방용품 / 18 화장품 / 20 농수축산물 / 21 가공식품 / 22 건강기능식품 / 35 기타재화.
  생활화학제품 코드는 공개 자료가 없어 플레이오토 화면에서 확인해야 한다.

## 지마켓·옥션

- 한 상품에 **옥션·지마켓 두 줄**이 필요하다. 쇼핑몰과 템플릿코드가 짝이어야 한다.
  ```
  옥션=redgoom00   → 2201548
  지마켓=redgoom00 → 2201554
  ```
- 금칙어를 상세설명에서도 막는다. 실제로 "알레르기"로 반려됐다.

## 공통

- **플레이오토 S3 썸네일(`s3-ap-northeast-2.../gmp01/`)은 만료되어 403이 난다.** 업로드 전 HEAD로 확인한다.
- **같은 판매자관리코드로 재업로드하면 "이미 존재"**로 막힌다. 플레이오토에서 지운 뒤 올린다.
- 상세설명은 엑셀 셀 한계 32,767자.

# 바코드

우선순위대로 찾는다. 여기까지 해도 없으면 실물 포장을 봐야 한다.

```
1. 코리안넷 (scripts/output/koreannet-catalog.json, 33,072건)  ← 이름에 용량이 있어 가장 정확
2. 식약처 C005 바코드연계 (258,080건)                          ← 용량 정보가 없어 다용량 제품은 모호
3. scripts/barcode-todo.mjs → 바코드_채울목록.xlsx              ← 사용자가 실물 보고 채움
```

매칭은 **틀리느니 비우는 쪽**으로 짠다. 확인된 실패 사례:

- 괄호 없는 단일 표기를 낱개로 읽으면 안 된다. `삼양 큰컵 불닭볶음탕면 1920g`은 16개들이 박스다.
  → `(120g x 5개입)` 꼴 괄호 표기만 신뢰한다.
- 이름이 비슷한 다른 맛·다른 제품에 붙는다(핫식스 포스↔제로, 웰치스 포도↔애플망고, 동원 꽁치↔리챔).
  → 우리 낱말이 후보에 전부 있어야 하고, 후보에만 있는 변형 낱말(제로·무가당·디카페인 등)이 있으면 버린다.

# 데이터 함정

- **임포트와 주문 매칭은 상품명으로 붙는다.** 이름이 완전히 같은 상품이 둘이면 한쪽만 연결되고,
  주문 원가가 엉뚱하게 붙는다. 등록 전에 이름 중복을 확인한다.
- 한글 뒤에서는 정규식 `\b`가 동작하지 않는다. `(?=\s|$)`를 쓴다.
- **Python heredoc은 `\b`를 백스페이스 문자로 바꿔 넣는다.** 정규식이 든 파일은 Write 도구로 고친다.
  (이것 때문에 수량 파싱이 조용히 망가진 적이 두 번 있다)
- Bash에서 Windows 경로는 `C:/Users/...`로 쓴다. `/c/Users/...`는 node에서 깨진다.
- 스크립트는 `scripts/` 아래에 둔다. 임시 폴더에서는 node_modules를 못 찾는다.
