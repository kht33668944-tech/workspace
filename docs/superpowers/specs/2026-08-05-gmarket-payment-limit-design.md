# 지마켓 자동구매 최종 결제금액 한도 검사 — 설계

날짜: 2026-08-05

## 배경

지마켓 자동구매 시 상품 쿠폰에 사용 가능 개수 제한이 있는 경우가 있다(예: 1인당 5개).
수량 7개 주문을 1개씩 반복 구매하면 6번째부터 쿠폰이 적용되지 않아 결제금액이 비싸지고,
정산예정금액보다 높은 가격에 구매되어 마이너스 마진이 발생한다.

이를 막기 위해 **"결제하기" 클릭 직전에 주문결제 페이지의 "최종 결제금액"을 읽어
회당 한도를 초과하면 결제하지 않고 실패 처리**한다.

## 요구사항

1. 결제 직전 최종 결제금액 검사: `최종 결제금액 > 회당 한도`면 구매 중단
2. 회당 한도 = `(주문의 정산예정금액 ÷ 수량) + 허용 적자`
3. 허용 적자는 자동구매 모달(결제 비밀번호 입력 화면)에서 입력
   - 비워두면 **0원** (적자 불허, 마진 0원은 허용 — 즉 한도와 같으면 진행)
   - 입력하면 그 금액까지 적자 허용
4. 중단 시 실제 결제는 발생하지 않고, 실패 사유가 `purchase_logs`에 남는다
5. 반복 구매(수량 2개 이상)는 **매 회차마다** 검사한다

## 변경 파일

### 1. `lib/scrapers/types.ts`
- `PurchaseOrderInfo`에 `maxPaymentPerUnit?: number` 추가
  - 회당 결제 한도(원). 미지정이면 검사 생략.

### 2. `components/workspace/orders/auto-purchase-modal.tsx`
- 설정(config) 단계에 "허용 적자" 숫자 입력칸 추가 (placeholder: 0)
- 주문별 한도 계산 후 `maxPaymentPerUnit`으로 전달:
  - `settlement > 0`인 주문: `Math.floor(settlement / quantity) + 허용적자`
  - `settlement`가 0이거나 없는 주문: 필드 미전달(검사 생략) — 정산예정금액이
    입력되지 않은 주문까지 전부 차단되는 것을 방지

### 3. `lib/scrapers/gmarket-purchase.ts`
- `processPayment()` 시그니처에 `order: PurchaseOrderInfo` 전달 (또는 한도 값)
- "결제하기" 버튼 클릭 **직전**, 결제할인 적용(`applyPaymentDiscount`) **이후**에
  주문결제 페이지의 "최종 결제금액" 파싱:
  - 우선 셀렉터 기반(주문 요약 영역), 실패 시 `body.innerText`에서
    `/최종\s*결제금액\s*([0-9,]+)\s*원/` 정규식 매칭
- 판정:
  - 파싱 성공 + `금액 > 한도` → 에러 throw (결제 안 함)
    - 사유: `"최종 결제금액 N원이 회당 한도 M원(정산 S원 ÷ 수량 Q + 허용적자 T원)을 초과해 구매를 중단했습니다."`
  - 파싱 실패(한도가 지정된 주문인데 금액을 못 읽음) → 에러 throw (안전 우선, 결제 안 함)
    - 사유: `"최종 결제금액을 확인할 수 없어 구매를 중단했습니다."`
  - 한도 미지정 주문 → 검사 생략, 기존 흐름 그대로

### 4. API route (`app/api/orders/auto-purchase/route.ts`)
- 변경 없음. `PurchaseOrderInfo`는 클라이언트에서 그대로 전달되며,
  스크래퍼가 던진 에러는 기존 실패 경로(`purchase_logs` 기록, 잠금 해제/부분구매 처리)를 탄다.

## 동작 예시

수량 7개, 정산예정 70,000원, 허용적자 500원 → 회당 한도 10,500원

- 1~5회차: 쿠폰 적용 결제금액 9,800원 → 통과, 구매
- 6회차: 쿠폰 소진으로 12,000원 → 한도 초과, 결제 중단
- 결과: 기존 부분구매 처리 — 구매된 주문번호들 기록, 주문 상태 "부분구매",
  실패 사유 로그 기록

## 에러 처리 원칙

- 금액을 확인할 수 없으면 결제하지 않는다 (false negative보다 안전 우선)
- 검사는 지마켓만 적용 (오늘의집은 이번 범위 외)
- 허용 적자 입력값은 0 이상의 정수만 허용

## 테스트

테스트 프레임워크가 없으므로 수동 검증:
1. `npx tsc --noEmit` 타입 체크
2. 정산예정금액이 낮은 테스트 주문으로 자동구매 실행 → 결제 전 중단 + 사유 확인
3. 정상 주문으로 자동구매 실행 → 기존과 동일하게 결제되는지 확인
