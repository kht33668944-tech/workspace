# 단체문자 일일 발송량 카운터 + KT 한도 차단 설계

**작성일:** 2026-08-18
**상태:** 승인됨 (구현 대기)

## 배경

2026-08-18 쿠팡 품절 안내 253건을 휴대폰(SMS Gate) 경로로 발송하던 중 KT로부터 아래 안내를 수신했다.

> [KT안내] 문자발송 제한안내
> 고객님의 문자 발송량이 일 300건을 초과하였습니다.
> 불법스팸방지를 위하여 일 500건 사용시 당일 문자발송이 제한됩니다

당일 실제 발송량은 오전 배치 76건 + 저녁 배치 253건 = **329건**이었다. 500건에는 못 미쳐 차단은 면했으나, 발송 시점에 누적량을 알 방법이 전혀 없었다는 것이 문제다.

한도(500건)에 걸리면 게이트웨이는 발송 요청을 정상 접수하고 `sms_logs`에도 `success`로 기록하지만, 통신사가 실제 발송을 막는다. 메시지는 큐에 남아 있다가 TTL(6시간, `SMS_GATEWAY_TTL_SECONDS`) 만료로 소멸한다. **즉 화면상 전건 성공으로 보이는데 고객에게는 한 통도 안 가는 상태가 된다.** 품절 안내처럼 미발송이 곧 클레임으로 이어지는 문자에서는 치명적이다.

## 목표

발송 전에 오늘 누적 발송량을 보여주고, KT 한도를 넘기는 발송을 실제로 차단한다.

## 비목표

- 500건 초과분을 자동으로 다음 날로 이월/예약 발송 — 이번 범위 밖
- SOLAPI 경로에 대한 한도 — SOLAPI는 KT 회선을 쓰지 않으므로 무관
- 한도 초과 시 자동 분할 발송 — 사용자가 선택을 줄이는 방식으로 해결

## 설계

### 1. 카운트 기준

`sms_logs` 테이블에서 아래 조건의 행 수를 센다.

- `user_id` = 현재 사용자
- `provider = 'phone'` (SOLAPI 제외)
- `created_at >= 오늘 KST 자정`

**KST 자정 계산:** 서버 타임존에 의존하지 않도록 UTC 기준으로 명시 계산한다.
`new Date(Date.now() + 9h)`로 KST 날짜를 구한 뒤, 그 날짜의 00:00 KST를 UTC로 환산(`-9h`)해 `created_at` 하한으로 쓴다.

**큐 접수 기준을 쓰는 이유:** 실제 발송(`Sent`) 기준으로 세려면 게이트웨이에 메시지 단건 조회를 발송 건수만큼 반복해야 해서 수 분이 걸린다(253건 실측 시 1~2분+, 타임아웃 다발). 큐 접수 기준은 실제 발송량보다 크거나 같게 잡히므로 한도 판단에서는 보수적(안전)인 방향이다.

**한계(수용):** KT의 카운트 기준일과 리셋 시각이 정확히 KST 자정인지는 공식 확인된 바 없다. 통상 기준을 따르되, 어긋날 경우 `SMS_DAILY_LIMIT`을 낮춰 마진을 확보한다.

### 2. 이중 검증

돈·발송처럼 되돌릴 수 없는 동작은 클라이언트 검증만으로는 부족하다. 오래 열어둔 탭의 구(舊) 번들은 새 검증 코드를 갖고 있지 않아 그대로 우회한다(과거 지마켓 결제 한도에서 겪은 문제와 동일한 구조).

| 계층 | 역할 | 실패 시 |
|---|---|---|
| `bulk-sms-modal.tsx` | 현황 표시, 발송 버튼 비활성화 | 사용자가 발송 전에 인지 |
| `app/api/sms/send/route.ts` | 발송 직전 서버에서 재계산 | HTTP 400 + 사유 반환 |

서버 검사는 `orders` 조회 후 `validOrders` 확정 직후, SSE 스트림을 열기 **전에** 수행한다. 스트림이 열린 뒤에는 에러를 깔끔히 전달하기 어렵고, 클라이언트가 이미 "발송 중" 화면으로 넘어간 상태가 되기 때문이다.

### 3. 임계값

| 구간 | 표시 | 발송 |
|---|---|---|
| `used + 선택 < 300` | 회색 정보 | 허용 |
| `300 <= used + 선택 <= 500` | 주황 경고 — KT 경고 문자 수신 가능 | 허용 |
| `used + 선택 > 500` | 빨강 차단 — 잔여 가능 건수 표시 | **차단** |

환경변수로 조정 가능하게 한다. 기본값은 KT 안내 문구 그대로.

```
SMS_DAILY_LIMIT=500   # 초과 시 발송 차단
SMS_DAILY_WARN=300    # 초과 시 경고 표시
```

`lib/sms-gateway.ts`에 상수로 노출해 서버·클라이언트가 같은 값을 쓰게 한다. 클라이언트는 값을 `/api/sms/daily-usage` 응답으로 받아 하드코딩을 피한다.

### 4. 신규 API: `GET /api/sms/daily-usage`

인증은 기존 라우트와 동일하게 `getAccessToken` → `getSupabaseClient`로 사용자 확인 후, 집계는 `getServiceSupabaseClient`로 수행한다.

**응답**

```json
{ "used": 329, "limit": 500, "warnAt": 300 }
```

조회 실패 시 발송 자체를 막지는 않는다(`used: null` 반환). 카운터는 보조 장치이므로, 집계가 안 된다고 발송 경로 전체가 죽는 것은 과하다. 단 이 경우 모달은 "사용량 확인 실패" 문구를 띄우고 서버 측 검사도 통과시킨다.

### 5. 모달 UI

발송 방식이 **휴대폰**일 때만 노출한다(SOLAPI 선택 시 숨김).

```
오늘 발송  329 / 500건
이번 발송  253건  →  합계 582건
⚠ 82건 초과. 최대 171건까지만 선택 가능합니다.
[ 발송 ]  ← 비활성화
```

초과 시 "몇 건까지 가능한지"를 숫자로 제시한다. 사용자가 선택을 몇 개 줄여야 하는지 바로 알 수 있어야 한다.

카운트 대상은 `recipients.length`(전화번호 유효성 필터 통과분)이지 `orders.length`가 아니다. 실제로 발송되는 건수와 일치시킨다.

### 6. 데이터 흐름

```
모달 열림
  └→ GET /api/sms/daily-usage → { used, limit, warnAt }
       └→ used + recipients.length 로 구간 판정 → 배너 + 버튼 상태

발송 클릭
  └→ POST /api/sms/send
       ├→ orders 조회 → validOrders 확정
       ├→ 오늘 사용량 재집계
       ├→ used + validOrders.length > limit ?
       │     └→ 400 { error: "...", used, limit }  ← 스트림 열기 전
       └→ SSE 스트림 시작
```

### 7. 에러 처리

| 상황 | 동작 |
|---|---|
| `daily-usage` 조회 실패 | 모달에 "사용량 확인 실패" 표시, 발송은 허용 |
| 서버 한도 초과 감지 | 400 + 토스트로 사유 표시, `compose` 단계 유지 |
| 서버 집계 쿼리 실패 | 발송 허용(카운터는 보조 장치), `console.warn` 기록 |

### 8. 검증 방법

테스트 프레임워크가 없으므로 수동 검증한다.

1. `SMS_DAILY_LIMIT=1`로 두고 2건 선택 → 모달 배너가 빨강, 버튼 비활성 확인
2. 같은 설정에서 브라우저 콘솔로 `/api/sms/send`를 직접 호출 → 400 응답 확인 (구번들 우회 방어 검증)
3. `SMS_DAILY_LIMIT=500` 복구 후 1건 실발송 → 카운터가 +1 되는지 확인
4. SOLAPI 선택 시 배너가 사라지는지 확인
5. `npx tsc --noEmit` 통과
